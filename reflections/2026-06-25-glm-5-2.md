## On the project

The architecture continues to hold up beautifully under sustained work. The stdlib-only core, the frozen-dataclass `Estate` contract, and the collector→ingest→pure-detector pipeline are clean and the "degrade honestly" discipline is consistently applied (every ACL-dependent detector has a skipped-passes degrade note; the unreadable-DACL path degrades to a per-template gap rather than a silent clear). The threat model as design spine is genuinely paying off — every detector maps to a row, and the `review-findings.md` ledger of resolved/low findings is a habit worth keeping.

What struck me this session: the project is at 1.0-readiness in its *detection* core (the ESC family is done and validated), but the *value-delivery* surface — making the output readable and actionable for the no-PKI-specialist persona the charter explicitly targets — is essentially absent (text/JSON only, no consequences prose, no evidence artifact, no narration). The deterministic core has outpaced the layer that would let a non-specialist actually use it. That's the honest gap, and it's why the backlog I filed leans on WI-015 (consequences catalogue) as the foundation everything else consumes.

## On the work done

The Deny-ACE fix is the work I'm most confident in and most want second eyes on, simultaneously. The conservative property (suppress only when *every* granting right is blocked) holds by construction, and the cross-model adversarial review (glm) proved it and validated the `_COVERS` implication map against Windows ACL semantics with no logic bugs found. I trust the no-false-negative direction.

What I'd want a second pair of eyes on: the **deviation**. To make `Allow GenericAll + Deny Enroll → suppressed` work correctly, `_ENROLL_RIGHTS` had to be narrowed from a 5-token set to `{enroll}`, which means an ACE granting *only* `AutoEnroll` no longer triggers ESC1/2/3/13/15. The reasoning (AD CS issuance is gated on the Enroll extended right, so AutoEnroll-alone never could obtain a cert) is sound and the reviewer endorsed it as correcting a latent false positive — but this is a Windows-semantics judgment call that changes detection results beyond the strict Deny scope, and it is **synthetic-test-only, not live-validated** against a real DACL with mixed Deny/Allow. The `_COVERS` map is reasoned, not measured.

The leak-guard + acl_obtained work is lower-risk and I'm confident in it. One thing I chose deliberately: I added the unreadable-DACL template to the *default* fixture (not a variant) and updated the two affected assertions, rather than keep a separate variant. That makes the default fixture more representative of a real export (which has some unreadable templates) and gives future tests the coverage for free — but it means any future test that counts findings exactly must account for the new `TEMPLATE_ACL_UNREADABLE`. Flagging that below.

The subagent-implementation + cross-model-adversarial-review workflow the user asked for worked well for the Deny-ACE change: the implementer (kimi) produced a clean implementation with one defensible deviation, and the reviewer (glm) caught zero logic bugs but surfaced three real doc/test gaps I then applied. The deviation was the genuinely valuable thing to pressure-test, and the review sharpened it.

## Gaps to flag

- **Deny-ACE precedence is synthetic-only, not live-validated.** The `_COVERS` implication map and the AutoEnroll-narrowing are reasoned from Windows ACL semantics, never measured against a real DACL carrying mixed Deny/Allow ACEs. The conservative property holds by construction, but the implication map's *completeness* (e.g., does `GenericWrite` cover a right it shouldn't, or miss one it should) is reasoning, not measurement. `detection.py` `_COVERS`. A positive live validation (a template with Allow Enroll + Deny Enroll, confirming ESC1 suppresses) would close this — mirrors how ESC8/10/11/13/14 were positive-validated on the lab.
- **The leak-guard identifier scan is dormant until the secret is set.** The always-on `samples/`-tracked-file guard is active in CI now, but the forbidden-identifier scan (the gpo-lens half) is a no-op until `ADCS_LENS_FORBIDDEN_IDENTIFIERS` is configured. That's the one manual pre-publication step (`WI-024`). `scripts/check_committed_identifiers.py`.
- **The `acl_obtained=false` template is in the default fixture.** Future tests that count findings exactly or assert "no TEMPLATE_ACL_UNREADABLE" must account for it. The two existing assertions were updated (`tests/test_ingest.py`), but a new test author could be surprised. `tests/fixtures/build_fixture.py`.
- **ESC15's live positive-validation status is not explicitly recorded.** AGENTS.md states ESC8/10/11/13/14 are positive-validated on the lab; ESC15 reuses existing collector data but its own validation (a v1 template on an unpatched CA) isn't clearly stated. Worth confirming/closing the validation matrix.
- **Local-run doc nit:** `scripts/check_committed_identifiers.py`'s docstring says `python scripts/check_committed_identifiers.py`, but in this env `python` isn't on PATH (only `.venv/bin/python`). The CI job uses `python` after `setup-python`, so CI is fine — only the local-run instruction would fail on a bare clone without the venv activated. Cosmetic.
