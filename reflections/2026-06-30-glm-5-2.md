## On the project

The threat-model-as-design-spine pattern is the keystone, and this session
confirmed it again from the *implementation* side. Adding ESC16 was a clean,
mechanically-guarded change precisely because the infrastructure built in prior
sessions does the heavy lifting: the verdict-aware traceability test
(`_IMPLEMENTED_VERDICTS`) meant flipping the ESC16 row from `Static (not yet
implemented)` to `Static` immediately *required* the detector to exist — I
literally could not forget the detector or the test would fail. The contiguity
guard was already satisfied (ESC1–16 is contiguous). The consequences-catalogue
AST guard meant the ESC16 entry had to exist or `test_catalogue_matches_every_
check_literal_in_detection` would fail. The `run_all` wiring guard meant I had to
call `detect_esc16` or `test_run_all_calls_every_detector` would fail. Every
guard is a forcing function for completeness, and they compose: I made four
interdependent changes (model + detector + catalogue + threat-model) and the
test suite told me immediately if any one lagged.

The frozen-dataclass `Estate` + pure-detector pattern continues to make this
codebase safe to extend. Adding `disabled_extensions` to `CertAuthority` with a
default `frozenset()` was backward-compatible by construction — no existing
construction site broke, and old exports without the field ingest to empty (no
false ESC16). That's the payoff of the disciplined model.

## On the work done

The highest-value move this session was **verifying ESC16 against the canonical
source before writing a line of detector code.** The 06-27 reflection's sharpest
lesson was that the adversarial review which surfaced ESC16 *also* hallucinated
ESC17 in the same breath — and the only thing that separated the real finding
from the phantom was checking Certipy's `find.py` against ground truth. So I
delegated an explore agent to extract the *exact* ESC16 detection logic from
Certipy's source. That extraction paid off three ways: it confirmed the OID
(`1.3.6.1.4.1.311.25.2`, bare, no prefix), confirmed the match semantics
(exact element membership, not substring), and — critically — revealed that
Certipy gates ESC16 on `will_issue and user_can_enroll` (attacker-context
preconditions). That last finding drove a deliberate design decision: adcs-lens
flags the *enabling CA configuration* without those gates, matching how ESC6
(CA-wide) and ESC9 (the direct analogue) are already implemented. Without the
verification step, I might have either copied Certipy's gating (wrong for a
defensive posture tool with no "current user" concept) or missed the exact-match
semantics.

The **two-reviewer parallel adversarial review** earned its keep. Both
independently caught the root-CA false-positive (an offline root doesn't issue
AD-auth end-entity certs, so the SID extension is irrelevant — flagging it would
be a false positive; ESC11 already skips `CaKind.ROOT`). The kimi reviewer
additionally caught a parser weakness (same-line multi-value REG_MULTI_SZ would
silently drop all but the first token) and the missing end-to-end integration
test. The glm reviewer gave a cleaner severity calibration argument (HIGH is
correct because exploitation requires an external precondition — weak DC
binding — making it an enabling config, not a direct primitive like ESC6's
CRITICAL). Running two reviewers in parallel rather than sequentially caught
more than either would have alone, and the areas of agreement (root-CA skip)
gave me confidence the finding was real, not a single reviewer's blind spot.

The one wrinkle: **the regista migration 35 block.** The `adcs_lens` schema has
a pending migration (from the `plan-012-regista-worktracking` branch) that
isn't applied, so every `agent-notes` command that touches the DB fails at

## Gaps to flag

- **The collector assigns the local CA's `DisableExtensionList` (and
  `EditFlags`, `InterfaceFlags`, `AuditFilter`) to *every* CA found via LDAP
  enrollment-services.** In a multi-CA forest run from one host, remote CAs
  inherit the local CA's config → false positives/negatives. Both adversarial
  reviewers flagged this; the kimi reviewer called it a BLOCKER. It's a
  pre-existing design limitation shared by ESC6/ESC7/ESC11/ESC16 (not a
  regression), and the collector is single-CA-on-host by design — but it's
  untracked. Worth a breadcrumb when the DB is writable. (`scripts/Export-
  AdcsEstate.ps1:298,319`).
- **No "obtained" marker for CA-registry reads.** A certutil parse failure
  (format drift) silently yields an empty `disabled_extensions` /
  `edit_flags` / `interface_flags` → a false negative indistinguishable from a
  genuinely clean CA. Templates have `acl_obtained` to distinguish "read but
  empty" from "not read"; CA-registry fields have no analogue. Shared by all
  certutil-backed CA detectors. Holistic design limitation, not ESC16-specific.
- **The parser `_parseCertutilMultiSzLines` is OID-scoped and lightly tested.**
  It captures the first whitespace-delimited token per continuation line
  (`^\s+(\S+)`), which is fine for bare OIDs but would truncate values with
  internal spaces if reused for a non-OID REG_MULTI_SZ. The Pester tests cover
  the common formats but not every certutil output variant — the live
  negative-validation step (AC) should confirm the format on the real lab.
- **Regista migration 35 is pending on the `adcs_lens` schema**, blocking all
  DB writes (work-item close, breadcrumb file, memory ingest). This is
  infrastructure work on the `plan-012-regista-worktracking` branch; the
  WI-036 close and this reflection's memory ingest are deferred until it's
  applied.
- **Plan 002 (`plans/002-precision-value-release.md`) still describes ESC16 as
  `Static (not yet implemented)`** in its "ground truth at time of writing"
  section. That's accurate as a point-in-time snapshot (the plan was proposed
  2026-06-30, before ESC16 was built this session), so I left it — but a reader
  of the plan should cross-reference the threat model for current state.
