## On the project

The threat-model-as-design-spine pattern continues to be the keystone, and
this session stress-tested it from the *ingest robustness* side rather than the
detector-completeness side. The architecture guard (stdlib-only core, no LLM in
truth path) held under review — no reviewer found a boundary violation, and
the AST-enforced traceability test means the design spine is genuinely
executable, not aspirational. The frozen-dataclass discipline paid off again:
the `certs_parsed` semantics change was backward-compatible by construction
because the field is a leaf, not a structural change.

What feels strongest: the *two-reviewer parallel adversarial review* pattern.
Running kimi + nemotron in parallel against the same code, then
cross-checking their claims against source, was the single highest-value
technique this session. It caught hallucinations in both directions —
nemotron's "GenericWrite covers WriteDacl/WriteOwner" was backwards (the code
was right per MS-DTYP), and kimi's "ESC6 root skip assumes offline" was a
design-philosophy disagreement, not a bug. Filtering reviewer claims through
source verification is non-negotiable for this kind of review; both reviewers
produced some confidently-wrong findings alongside real ones.

What feels fragile: the ingest layer's type coercion was previously loose
(raw `ca.get("audit_filter")` passed straight through), and the detectors
downstream assumed `int`. That's a latent `TypeError`-on-real-export class of
bug that the test suite didn't catch because the synthetic fixture always
emitted the right types. The real collector (PowerShell) is more likely to
emit strings. The `_coerce_int` / `_coerce_bool` helpers close this, but the
pattern — "ingest trusts the JSON shape; detectors assume Python types" — is
worth a project convention note so future fields don't repeat it.

## On the work done

The highest-value move was **verifying reviewer claims before acting on
them.** Both adversarial reviewers produced CRITICAL findings that were
hallucinations:

- nemotron's "CRITICAL: `_COVERS` missing GenericWrite→WriteDacl/WriteOwner" —
  backwards. Per MS-DTYP, GenericWrite does NOT cover control rights; the code
  comment at `detection.py:92-93` is correct. If I'd "fixed" this I'd have
  introduced false positives.
- nemotron's "ESC10 UNKNOWN binding should be treated as PERMISSIVE" — a
  posture-tool philosophy choice, not a defect. The current INFO note is the
  honest read.
- kimi's "ESC16 root skip assumes all roots are offline" — partially valid but
  low priority; an online root issuing end-entity certs is uncommon.

The lesson: an adversarial review is a *signal generator*, not a *work list*.
Every CRITICAL claim gets verified against canonical semantics before it earns
a fix. This is the same discipline the 06-30 reflection recorded ("verifying
ESC16 against the canonical source before writing a line of detector code"),
generalized to the review layer.

The second-highest move: **running a second adversarial round on the fixes
themselves.** The first round's fixes were correct in intent but incomplete in
execution — the CRL-only `certs_parsed` gap (I'd only set the flag in the cert
loop, not the CRL loop) and the `regressions`-property inconsistency (the CLI
gate filtered degrade notes but the `DriftReport.regressions` property didn't,
so JSON `summary.regressions` would say True while `--exit-code` returned 0)
were both caught only because I ran the reviewers again on the diff. A single
review pass would have shipped both. The two-round pattern (review → fix →
review-the-fix) is now the default for non-trivial changes.

The one wrinkle: **the regista migration 38/39 is pending on the `adcs_lens`
schema**, blocking all DB writes (work-item filing, breadcrumb filing, memory
ingest). This is the same class of blocker the 06-30 reflection noted (then it
was migration 35). The code work is complete; the bookkeeping is deferred
again. I could not file the breadcrumb for the `CertAuthority.roles` dead-data
gap (newly noticed this session) for the same reason.

## Gaps to flag

- **Regista migrations 38-39 are pending on the `adcs_lens` schema**, blocking
  all DB writes (work-item close/file, breadcrumb file, memory ingest). This
  is infrastructure work on the `plan-012-regista-worktracking` branch. Until
  applied, the `CertAuthority.roles` dead-data breadcrumb and this reflection's
  memory ingest are deferred. (Same blocker as 06-30, now advanced by two
  migrations.)
- **The ingest→detector type contract was implicit and is now explicit via
  `_coerce_int`/`_coerce_bool`, but only on the fields that triggered the
  review.** Other numeric/bool fields ingested elsewhere (e.g. `schema_version`
  has bespoke coercion at `ingest.py:284-290` — not reused via `_coerce_int`)
  follow the same implicit-trust pattern. Worth a sweep to apply the helpers
  uniformly, or a convention note in AGENTS.md.
- **The `DriftReport.regressions` property now filters degradation notes via
  `is_degradation_note`, coupling `diff.py` to `detection.py`'s note set.**
  This is the right call (gate + JSON + text all agree), but it means
  `test_degradation_notes_set_stays_in_sync` (`test_threat_model_traceability.py`)
  now indirectly guards the diff gate too. Worth knowing.
- **The ESC6 docstring rationale was rewritten after both reviewers flagged the
  "propagate down the chain" claim as inaccurate.** The flag is per-CA, not
  inherited — a root with EDITF_SAN2 honors requester SANs on certs *it* issues
  (subordinate CA certs), which is a configuration smell but not a chain-wide
  propagation. The detector behavior (flag all CA kinds) is unchanged and
  correct; only the docstring was wrong.
- **Two adversarial reviewers produced confidently-wrong CRITICAL findings
  alongside real ones.** This is a property of the reviewer pattern, not a
  bug — but it means reviewer output must be verified against canonical
  semantics (MS-DTYP, the threat model, the actual source) before acting. The
  "CRITICAL: _COVERS is wrong" finding from nemotron would have introduced a
  false positive if applied blindly.
- **The `samples/` calibration workflow is documented but unimplemented.**
  `AGENTS.md` build section lists `.venv/bin/pytest -q -m samples` and
  `pyproject.toml:57` registers the marker, but no test carries the mark. This
  is a capability claim that doesn't exist — either implement calibration
  tests (guarded by `samples/` presence) or remove the marker + doc claim.
