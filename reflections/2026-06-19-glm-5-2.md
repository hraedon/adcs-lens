## On the project

The architecture paid off again: the model was *already* ESC11/13-ready
(`CertAuthority.interface_flags`, `CertTemplate.issuance_policy_oids`,
`IssuanceOid.group_link_sid`, `Estate.oids` all pre-existed from the collector's
Phase 1b work), so both detectors were pure additions to `detection.py` — zero
model/ingest churn, exactly the "small pure functions over the same Estate"
property the prior reflection praised. The "validate against reality" discipline
remains the spine: ESC11/13 produced the *correct* CLEAN result on the real
`ad-LABCA01` export (flag present; all OIDs group-link-null), which is strong
evidence they aren't dead code or mis-keyed. Delegating implementation to
kimi/glm subagents and gating each on an adversarial reviewer worked well — the
reviewers caught a genuinely misleading test name, real test-coverage holes, *and*
the pre-existing severity-sort bug that I'd have shipped otherwise.

The central tension this session was **lab access**. The user assumed an
`agent-capability-broker` would grant live CA access; it doesn't exist in my tool
set or MCP config. The host is network-reachable (RPC 135 open) and `pwsh` is
installed, but the collector needs domain creds I don't have. I surfaced this
immediately rather than pretending, and redirected to the offline-capable
roadmap — the right call, but it means ESC5 and *positive* ESC11/13 validation
(the kind that caught the `_decode` bug last session) are still owed. The user is
working on the ACB.

## On the work done

**Confident in:** ESC11/13 logic (reviewed twice, faithful to the threat-model
rows, clean on real data, each gate has a positive+negative test). The
`acl_obtained` signal is backward-compatible by construction (old exports default
True → zero spurious `TEMPLATE_ACL_UNREADABLE` notes, verified on both
`samples/` exports). The severity-sort fix is a clear correctness win and now has
a test that actually fails under the old alphabetical behavior.

**Judgment calls I'd want a second pair of eyes on:**
- **ESC13 requires a client-auth EKU** (`_can_authenticate`). Defensible — the
  issuance-policy→group escalation is realized on authentication, so a
  code-signing-only template can't deliver it — but it's a stricter reading than
  the threat-model table literally states ("template msPKI-Certificate-Policy +
  msDS-OIDToGroupLink"). Documented in the docstring; easy to relax.
- **ESC11 excludes root-kind CAs.** Correct for the two-tier offline-root case,
  and safe because the collector only ever emits `kind='issuing'` — but it's a
  heuristic. A standalone root serving enrollment wouldn't be flagged.
- **ESC11 = HIGH while ESC6 = CRITICAL.** ESC6 is a direct CA-wide escalation;
  ESC11 is an enabling config for a relay (relay not confirmed). I think the
  split is right; a stricter shop might argue ESC11 CRITICAL.

**Awkward but harmless:** ESC13's detail string does a `polic`+`y/ies`
pluralization split across f-strings. Works, reads slightly odd.

## Gaps to flag

- **ESC11 has no degradation path** for silent `certutil -getreg` failure
  (`detection.py` `detect_esc11`). An empty `interface_flags` is ambiguous
  ("flag genuinely absent" vs "collection silently failed"). This is *consistent*
  with ESC6 (same source, same property) and mitigated by the collector's
  `$ErrorActionPreference='Stop'`, so I deliberately did not diverge — but it's a
  systemic ambiguity in the flags-collection path worth noting. Low severity.
- **`published_by` and deny-ACE precedence** remain open LOWs in
  `docs/review-findings.md` (unchanged this session).
- **PR #10 and PR #9 (ESC4) both touch `detection.py`** in non-overlapping
  regions; they rebased cleanly independently, but whichever merges second will
  need a trivial rebase. Not a conflict, just sequencing.
- **`agent-capability-broker` is not wired into this opencode config** (only
  regista-eventlog / git-constellation / zread / web / playwright MCP servers
  exist). If the user gets the ACB working, it likely needs an MCP or tool entry
  here before agents can use it.
