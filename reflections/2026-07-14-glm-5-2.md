# Session Reflection — 2026-07-14

**Work summary:** The user asked for a review + a drive toward a solid 1.0/MVP
with subagents, adversarial review, and green CI. On orienting, the project was
*already* at v1.0.0 on main, CI green — the 07-06 session had shipped the
deterministic core + Phase-1 honesty/precision work. So the real job was (a)
verify ground truth, because a **discrepancy** existed: WI-019/025/027/034/036
were open in the DB but implemented in the 1.0 commit `8053c7e`, and Plan 002's
WI-number mapping was scrambled relative to the DB; and (b) close the genuine
remaining gaps with the project's discipline.

Implemented three MVP-appropriate, low-risk features on top of the deterministic
core: **WI-031** collector/core minimum-version compatibility check at ingest
(warns on stderr when a collector predates `0.5.0` — a stale collector silently
omitting `csp`/`owner_sid`/`ca_patch_state` reads as a false all-clear; this is
trust-contract insurance); **WI-022** CRL early-warning window (a CRL within
`max(1 day, 25% of its own validity)` of nextUpdate flags HIGH/CRITICAL before it
goes critical-expired — the absolute `--warn-days` is wrong for short CRLs, so
the window is proportional, floored to one day only when strictly inside the
validity period); and **WI-033** group-token-expansion caveat surfaced in
`doctor` output as an estate-level INFO note `ACL_GROUP_TOKEN_CAVEAT` (the ACL
detectors match the trustee SID directly; nested-group membership is not
expanded, so a "no finding" is not proof of no path — now visible, not just a
code comment). Bumped the fixture's collector_version to `0.5.0-fixture`,
tightened the README's ESC15 patch-state wording (the field is `unknown` today),
and corrected `--warn-days` help text.

Ran **two independent adversarial lineages** (kimi + glm implementer agents —
dedicated reviewers are usage-locked per the user). Both converged on a real
false-positive vector I had introduced: the 1-day CRL floor made any CRL with
validity ≤ 1 day fire HIGH **from the moment of publication** (short-lived CRLs
are common → persistent noise that trips `--exit-code`). Fixed by applying the
floor only when `window < 1 day < validity`, so `window < validity` always holds
and a fresh short CRL is never flagged. Both reviewers also caught a misnamed
duplicate test, `v`-prefixed version strings silently rejected, stale help text,
and the `CRL_EXPIRY` consequence entry under-describing the early-warning state —
all fixed. Added a dedicated regression test for the short-CRL-from-publication
case. 347 pytest + ruff + mypy --strict green.

Filed **WI-038** (ESC9 fires HIGH with no enrollability/manager-approval gate —
the most concrete untracked false-positive vector, found by the review; recorded
as a decision to revisit, not silently changed) and **WI-037** (ESC7 cannot
model owner-based control — `CertAuthority` has no `owner_sid`, asymmetric with
ESC4/ESC5). Closed the WIs the 1.0 commit resolved but the DB never transitioned.

## On the project

The keystone observation from the 07-06 reflection holds and was re-confirmed:
the **threat-model-as-design-spine + AST-enforced traceability guard** is what
makes fast, safe change possible. This session added a detector
(`detect_acl_coverage_caveats`) + an INFO check + a consequence entry, and the
guard caught nothing — because the wiring was complete (a testament to how
legible the contract is). The four invariants (every `detect_*` in `run_all`;
every `check=` literal in `CONSEQUENCES`; every INFO check in
`_DEGRADATION_NOTES`; hygiene rows accounted for) make "did I wire it
everywhere?" a compile-time question, not a review question.

What is strongest here is the **two-lineage adversarial-review pattern catching
a real bug the author and a single pass would miss.** Both reviewers
independently computed that a 24h CRL fires at publication — that convergence is
the signal it was real, not a hallucination. This is the project's own
discipline (the 07-06 session's round-2 caught the offline-root patch-state
bug) and it works. The lesson reinforced: **a detector that adds a time window
must be tested at the boundary of "freshly published"**, not just "near
expiry" — the floor/validity interaction is exactly the kind of edge that looks
fine in the happy-path test and bites in production.

What is fragile: the **work-item DB drifts from the code** when commits don't
say "resolve WI-X". The `reconcile` command couldn't catch the 1.0 resolutions
because the commit message named topics, not identifiers. Five open WIs were
already done; the plan document's WI-number mapping was scrambled. This is a
process smell — the DB is only as honest as the last session's discipline to
close-what-it-shipped. A convention (commit-message trailers `Closes WI-X` that
`reconcile` matches) would pay for itself here.

## On the work done

The highest-value move was **recognizing the project was already at 1.0 and
resisting scope-creep into the narration layer (WI-016).** Narration is the
charter's flagship, but it needs an LLM SDK + API key, breaks the air-gappable
core unless behind a strict boundary, and Plan 002 *explicitly decided* to defer
it ("publish after Phase 1, narration follows in the open"). Driving to a
*solid* 1.0 meant the honesty/precision/completeness polish (WI-031/022/033),
not the reach feature. The right call was to respect a documented decision
rather than re-litigate it.

The trickiest judgment call was **ESC9: record, don't change.** The review found
a genuine inconsistency (ESC9 fires on the flag alone, unlike ESC1/2/3 and
ESC10/ESC14). But the current behavior *matches the threat-model verdict*
("Static from the flag"), the docstring + dedicated tests encode a *deliberate*
design choice ("evaluates on every export, no ACL dependency"), and tightening
it is a detection-semantics reversal that risks a **false negative** — the worst
outcome for a defensive tool. The project's culture (visible across every
reflection: ESC6-on-root, ESC15-no-CA, property-scoped WriteProperty) is to
*document and track* ambiguous detection questions, not silently reverse them.
So WI-038 records the decision with the option space; it does not hide it. If a
future agent disagrees, the FN-safe subset (enroll + manager-approval gates, which
can only suppress non-attacker-reachable templates) is clearly identified.

The **CRL floor fix** is the change most worth a second look: the inequality
`if window < timedelta(days=1) < validity: window = timedelta(days=1)` guarantees
`window < validity` always (fractional window < validity since 0.25 < 1; floored
window = 1 day < validity by the guard). So a freshly-published CRL
(`remaining == validity`) always has `remaining > window` → never flagged. The
regression test pins this. Clean.

## Gaps to flag

- **`ca_patch_state` is always "unknown" in practice** — the collector emits it
  verbatim; ESC15's HIGH branch is unreachable on a real estate (always MEDIUM).
  The README now says so; the field is forward-looking, not populated. A future
  collector enhancement could read the CA host's OS build, but that is fragile
  and needs live validation.
- **The `diff` contract keys on `(check, subject, source)`** (structural
  observation from the review): a cosmetic `source`-string edit becomes a
  regression+resolve pair in `diff`. There is **no test guarding source-string
  stability** the way the traceability test guards check-id stability. Worth a
  thought before public consumers depend on `diff --exit-code`.
- **The collector-compat warning goes to stderr** — correct Unix behavior, but a
  pipeline that merges streams (`2>&1 | jq`) before a JSON/SARIF parse would
  break. Left as conventional stderr; documented here so it is a known, not
  silent, trade-off.
- **Live validation of the v0.5.0 collector fields** (csp/owner_sid/
  ca_patch_state/GENERIC_ALL decode) is still the biggest *untracked* risk to the
  "evidence-producing" claim — the Windows-only paths have no Linux CI coverage
  and no live run since they were added. Not a code gap; an operational one.
