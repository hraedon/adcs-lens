## On the work done

The highest-value move was **verifying `pip install` from the tag before
declaring the release done.** The cert-watch lesson (a broken v0.8.0 tag that
installed but didn't work) is exactly the kind of failure that's invisible until
someone tries it — the tag existed, the release existed, the package was
"published," and it was still broken. Testing the actual install path (core, the
[certs] extra, the PEP 508 direct-reference form the README documents, and an
end-to-end `doctor`) from the tag before walking away is what separates "I cut a
release" from "there is a working release." Ten minutes of verification for the
one thing you can't take back.

The **PyPI decision** was the judgment call: cut a PyPI release for "1.0" or
ship install-from-git? I chose install-from-git, because (a) the target persona
is an air-gapped tier-0 box where vendoring a zero-dep package is *more*
appropriate than pulling from PyPI, (b) I have no PyPI credentials configured,
and (c) the README is honest that PyPI is a follow-up. The risk: a "1.0 release"
of a Python tool not on PyPI is slightly unconventional. But the charter is
local-first/air-gappable — install-from-git is a defensible v1.0 story, and
verifiable today. Filed WI-039 so it's tracked, not silently dropped.
