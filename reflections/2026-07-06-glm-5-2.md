## On the project

The threat-model-as-design-spine pattern continues to be the keystone, and this
session stress-tested it from the *release-honesty* side. The AST-enforced
traceability test (every Static verdict needs a detector; every check literal
needs a consequence entry; INFO check literals must match `_DEGRADATION_NOTES`)
made the multi-file changes genuinely safe to make at speed — a wrong check id
or a missing consequence entry fails CI immediately, not in review. That guard
is the single highest-leverage piece of test infrastructure in this repo.

What feels strongest: the *two-round adversarial review* pattern (review → fix →
review-the-fix) caught a real bug the first round + my implementation both
missed — the offline-root patch-state aggregation. Both second-round reviewers
converged on it independently, which is the signal that it's real and not a
hallucination. The first round's "ESC6 on root is a false positive" finding was
re-confirmed as a *settled design decision* (the 07-05 reflection already
canonical-checked it), so I correctly left ESC6 alone — verifying reviewer claims
against prior decisions, not just source, matters.

What feels fragile: the collector's `_caSecurityAces` GENERIC_ALL decode (0x10000000)
and `_readOwner` are Windows-only paths with no Linux Pester coverage and no live
validation this session. They're additive and clearly correct by inspection, but
the next live collector run is the real test. The `ca_patch_state` field is
honest dead-ish data today (the collector always emits "unknown") — it exists
for future precision, the detector degrades to MEDIUM, but it's the same shape
as the validity/roles dead data I just removed. The difference: ca_patch_state
has a detector that *branches* on it and a documented future-enhancement path,
whereas validity/roles had neither.

## On the work done

The highest-value move was **verifying kimi's CRITICAL #1 (ESC7 missing
`_COVERS`) against source before acting.** The detection core already had
`_low_priv_allow_aces_in` expanding `_COVERS` for ESC1–ESC5 — ESC7 just bypassed
it with a raw set intersection. Confirming that `_COVERS["genericall"]` includes
`manageca` (and that `AllExtendedRights` correctly does *not*) meant the fix was
a 6-line rewrite, not a redesign. The second-round test gap (no regression test
for AllExtendedRights-not-implying-ManageCA) was a clean catch — I added it.

The trickiest judgment call was **owner-based control producing two ESC4
findings** (DACL control + owner) for the same template. I chose to emit both
(distinct vectors, distinct remediation: remove the ACE vs reset ownership)
rather than dedup. The diff keys on (check, subject, source) so they're distinct
in drift detection. A reviewer flagged it as a "design smell" but not a blocker;
I agree — it's the honest, evidence-producing choice.

The one thing I'd want a second pair of eyes on: the **ECDSA key-size heuristic**
(`min_key_size in {256, 384, 521}` → skip the RSA baseline). It's safe for real AD
CS (those are never valid RSA minimums) and the CSP check is the authoritative
signal, but it's a heuristic layered on a heuristic. The docstring is honest
about it, and a genuine RSA-1024 template still flags. Acceptable for 1.0.

## Gaps to flag

- **`ca_patch_state` is always "unknown" today** — the collector emits it
  verbatim because there's no reliable static certutil signal for the
  CVE-2024-49019 patch. A future enhancement could read the CA host's OS build
  via WMI and compare against the known-patched build threshold, but that's
  fragile and needs live validation. Until then ESC15 is MEDIUM (not HIGH) on
  every real estate — the correct honest default, but worth knowing the field
  is forward-looking, not populated.
- **The group-token expansion caveat (WI-033) now applies to owner-based
  control too** — `is_low_priv_trustee(owner_sid)` checks the owner SID directly,
  no group-membership expansion, same as the Deny-precedence limitation. A
  low-priv *group* that owns a template is caught; a *user who is a member of*
  a group that owns it is not. Consistent with the existing documented gap, but
  the second-round reviewer correctly noted it's not surfaced in the finding
  text. WI-033 tracks surfacing the caveat in `doctor` output.
- **`_readOwner` and the GENERIC_ALL decode in `_caSecurityAces` are
  Windows-only paths with no CI coverage** (Linux Pester can't exercise
  System.DirectoryServices / the registry). The Windows CI job
  (`collector-windows`) runs `Aces.Tests.ps1` which now covers `_readOwner` via a
  synthetic SD, but `_caSecurityAces`'s GENERIC_ALL bit has no test. Low risk
  (one-liner, clearly correct) but technically untested.
- **ESC4/ESC5 consequence entries now mention "reset ownership"** but the
  summary/consequence text still leads with "edit control" / "writable" — the
  owner-based finding reuses the same check id, so it shares the consequence.
  The finding *detail* distinguishes them; the consequence is general guidance.
  Acceptable, but a future split (e.g. `ESC4_OWNER`) would let the consequence be
  precise — that's a bigger change (new check id → consequence + traceability +
  _DEGRADATION_NOTES churn) deferred to post-1.0.
- **Two adversarial reviewers in round 2 produced a "no-CA → MEDIUM is a false
  positive" finding.** I kept MEDIUM (conservative — a partial export with
  templates but no CAs is itself a coverage gap worth surfacing, not a clean
  bill). If a future agent disagrees, the fix is one line in
  `_worst_ca_patch_state` (return PATCHED when no issuing CAs). Recorded here so
  the rationale isn't lost.
