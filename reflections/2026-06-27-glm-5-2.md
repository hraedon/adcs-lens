## On the project

The threat-model-as-design-spine pattern is the keystone, and this session
exposed its one structural blind spot — then closed it. The traceability test
verified that ESC classes *present in the threat model* had detectors, which
meant a class missing from **both** the model and the code passed silently
(ESC12). I replaced that with a verdict-aware check (only `Static` verdicts
require a detector) plus a **contiguity guard** (ESC numbers must be 1..max with
no gaps). That guard is the real fix: a number can now be skipped only with an
explicit `Out` verdict, never by omission. I verified it fails exactly as
intended when ESC12 is removed.

The frozen-dataclass `Estate` + pure-detector pattern absorbed three more
changes (a new diff delta shape, a degradation-note set, a new verdict
category) with zero structural change to the model. The consequences-catalogue-
as-data and AST-guard discipline continues to make this codebase safe to extend:
adding the `_DEGRADATION_NOTES` drift guard was a 15-line test mirroring the
existing catalogue guard, and it mechanically prevents WI-030's fix from rotting.

## On the work done

The ESC12 research was the hard part and the part I'm most satisfied with.
ESC12 is genuinely undocumented — absent from Certipy's `find.py` enumeration
engine, absent from SpecterOps/Unit 42/Hacker Recipes. The honest move was
**not** to fabricate a detectability verdict (wrong security classification is
worse than the gap) but to document it as `Out (unresolved)` with the research
finding recorded. That keeps the catalogue complete without overclaiming.

The glm adversarial review earned its keep twice and taught a sharp lesson.
First, it surfaced **ESC16** — CA-wide security-extension disable via
`disabled_extensions` containing `1.3.6.1.4.1.311.25.2` — which is real,
statically detectable, and which the catalogue omitted. That's the exact
tail-omission failure mode WI-026's contiguity test *cannot* catch (it guards
1..max, but if the max itself is wrong the test passes cleanly). I added ESC16
as `Static (not yet implemented)` and filed WI-036. Second, the review also
claimed an **ESC17** ("Server authentication template with enrollee-supplied
subject") — which is a **hallucination**; it is not in Certipy's `find.py`. I
verified by grepping the canonical source before acting, and skipped it. That
verification step is the lesson: adversarial reviews are valuable but not
infallible; a reviewer that finds one real thing (ESC16) and one phantom
(ESC17) in the same breath is exactly why you check against ground truth before
applying.

The WI-028 diff fix had a subtle bug I caught in my own rewrite: my first
version used `delta.worsened or delta.content_changed` to decide "changed", but
a severity **improvement** has `worsened=False` and `content_changed=False`
(severity differs → content_changed short-circuits), so it would've been
counted as "unchanged" — silently dropping a severity-better delta. The
original code flagged any severity difference. I corrected it to
`of.severity != nf.severity or delta.content_changed`, which is exact and keeps
the tuple comparison in one place.

## Gaps to flag

- **The contiguity test guards mid-range gaps, not tail omissions beyond the
  declared max.** It enforces 1..max where max is the highest number *in the
  catalogue*. If a real ESC17/ESC18 emerges in canonical tooling and nobody
  adds it, the test still passes. ESC16 only got added because the adversarial
  review happened to surface it. Mitigation is human: the catalogue tracks the
  ESC classes Certipy's `find.py` implements; a deliberate check is needed when
  extending. A mechanical tail-guard would require coupling to an external
  source of truth that doesn't exist in-repo.
- **ESC12's `Out (unresolved)` verdict is honest but means the catalogue
  claims a class it cannot classify.** If a future researcher defines ESC12 as
  statically detectable, the verdict must be revisited (and a detector built).
  The contiguity test will at least force it to stay present — it can't go back
  to silent absence.
- **The `INFO == degradation note` convention is implicit.** The new
  `test_degradation_notes_set_stays_in_sync` guard locks `_DEGRADATION_NOTES`
  to the INFO-severity check literals, so drift is caught — but the *rule*
  that INFO severity is reserved for coverage-gap notes (never real posture
  findings) lives only in convention. A future real-INFO finding would force a
  decision via the guard (good friction), but the convention isn't documented
  in AGENTS.md.
- **WI-028's "content-only change does not trip `--exit-code`" is a deliberate
  call that hides a class of real regressions from the CI gate.** A widened
  enroller set on an ESC1 template (same CRITICAL severity) is strictly worse
  posture but won't trip `diff --exit-code` — it's only visible in the
  `changed` output. The `--exit-code` help text now states this, but an
  operator who only checks the exit code will miss it. A future `--strict`
  flag (WI-level) would close this if it matters in practice.
- **`detect_esc7`'s `by_trustee` dict keys on the raw `ace.trustee_sid`**
  (detection.py:646) rather than the normalized form used elsewhere — latent
  split if the collector ever emits mixed-case SIDs for the same trustee
  across ACEs. Tracked in the WI-035 output-polish bundle, not fixed this
  session.
- **The new detectors/guards are synthetic-fixture-tested only.** None of
  this session's work ran against the real gitignored `samples/` export (the
  `-m samples` suite skips in CI). A calibration run would confirm the
  contiguity/verdict parsing behaves on the real threat-model file — though
  since the threat model is hand-authored and the tests parse it directly,
  this is low-risk.
